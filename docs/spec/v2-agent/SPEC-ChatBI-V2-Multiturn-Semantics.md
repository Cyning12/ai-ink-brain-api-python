## 1. 文档定位与边界

### 1.1 要解决什么问题

总规 **§2.6** 约定：同一 `session_id` 下，后端可从 `rag_conversation_logs` **加载**历史，并在 Intent / 工具侧注入 **最近若干条** 对话。这解决的是 **「会话是否连续」**（transport + memory **可达性**）。

本子规讨论的是第二层问题：**「追问是否在语义上接得住」**——例如首轮明确查 `agent_info` 行数，次轮问「刚刚查询的表里有多少是男性」时，系统是否仍能生成 **针对同一表、且列语义正确** 的查询或回答。

> **结论**：**session 正确 + 历史非空 ≠ 追问一定成功**。失败可能来自指代未消解、SQL 列值约定、空结果、或工具路径切换；需在 SPEC 层拆开表述，避免与 L6「同 id 两轮」验收混为一谈。

### 1.2 非范围

- **HTTP / SSE / `session_id` 字段**：见总规 §2.6、§7.5.5.1。  
- **前端 transcript / Timeline UI**：见 `ai-ink-brain` 任务单与 `_tech_graph`。  
- **增量 SSE Timeline vNext**：见 `SPEC-ChatBI-V2-Incremental-SSE-Timeline-vNext.md`。

## 2. 概念分层

| 层级 | 含义 | 典型验收 |
|------|------|----------|
| **L0 传输** | 每轮请求带同一 `session_id` | Network Payload 一致 |
| **L1 记忆可达** | `AgentMemoryStore.load` 非空；Intent / `call_history` 含上轮文本 | 日志或 admin 可见 history 块 |
| **L2 意图承接** | 次轮仍判为 `text2sql`（或合理 fallback），且 **工具名与业务意图一致** | `agent.intent` 人工可读 |
| **L3 指代消解（grounding）** | 「该表」「刚刚的查询」解析为 **具体表 / 上轮 SQL 语义锚点** | 次轮生成 SQL 显式含 `agent_info`（示例） |
| **L4 结果真值** | SQL 执行结果与业务数据一致；「未查到数据」区分 **空集** vs **错查** | DB 对照 / `tool_results` |

**纸面目标**：产品宣称「多轮问数」时，至少应达到 **L1 + 在 SPEC 中声明的 L2/L3 策略**；否则仅宣称「多轮会话」易与用户预期冲突。

## 3. 指代与 Query Rewrite（可选能力）

### 3.1 定义

- **指代消解（coreference / grounding）**：将当前轮 `query` 中的省略主语、指示代词、「刚刚那张表」等，绑定到 **可执行工件**（表名、schema、上一轮主 SQL 的语义摘要等）。  
- **Query rewrite（NL → NL）**：在调用 Intent 或 Text2SQL 核心前，增加一步（模型或规则），输出 **自包含** 查询句，例如明确写出 `agent_info` 与「性别」对应列的业务含义。

二者可合并实现，也可只做强 history、不显式 rewrite；**本子规不强制唯一实现路径**，但要求在任务 / PR 中写清选型，便于回归。

### 3.2 与现有管道的关系（概念）

| 组件 | 当前角色（参见总规 §2.6.2） | 与多轮语义的关系 |
|------|------------------------------|------------------|
| `AgentMemoryStore.load` | 提供最近若干 `{query, response}` | 提供 **L1** 文本锚点 |
| `intent_agent` | `history_block`、最近 6 条 role | 可能隐含 **L2**；是否足以完成 **L3** 依赖提示词与模型 |
| `api/agent.py` | `turn_history[-6:]` 传入工具 | Text2SQL 是否「看懂」指代依赖 **prompt + 是否注入结构化锚点** |

**缺口类型（示例）**：仅拼接自然语言历史时，次轮 LLM 仍可能生成 **未带上一轮表名** 的 SQL，或性别枚举与表内实际取值不一致 → 用户看到「未查到数据」，但根因不在「没开多轮」。

## 4. 结构化上下文（推荐方向，非当前阻断）

以下作为 **V2.x / P1+ 增强** 的可选规格，便于与「加一句 rewrite」之外的路线对齐：

1. **表级锚点**：上一轮 Text2SQL 若已解析主表，将 **resolved_table**（或等价物）写入当轮内存或日志扩展字段，供次轮工具提示使用。  
2. **SQL 语义摘要**：将上一轮 **可公开** 的 SQL 摘要（脱敏后）注入 tool 侧 history，而非仅 assistant 自然语言答复。  
3. **澄清策略**：当指代置信度低时，SSE 返回追问（「您是指上一张表 agent_info 吗？」）优于盲执行 —— 与总规 **§2.4** fallback / 追问精神一致。

实现落点、字段名、表结构以 `PROJECT_CONFIG`、`rag_conversation_logs` 迁移与代码为准；本子规不虚构列名。

## 5. 用户可见结果与排障语义

### 5.1 「未查到数据」类回复

应区分（至少在内部日志或 `error_code` 语义上）：

| 情况 | 用户感知 | 建议内部区分 |
|------|----------|----------------|
| 执行成功、结果集行数为 0 | 常与「查错条件」难以区分 | 记录实际 SQL + `rows=0` |
| SQL 语法 / 权限 / 表不存在 | 可能仍被包装成笼统话术 | 已有 `error_code` 矩阵（总规 §2.4） |
| 未走 SQL 或历史未注入 | 答非所问 | Intent / mode 与 `call_history` 长度 |

**多轮专项排障**：次轮请求到达后，优先核对 **(1)** `session_id` **(2)** `load` 行数 **(3)** 次轮 `agent.intent` / 最终执行 SQL 是否含首轮锚点表。

### 5.2 与 L6 验收的关系

- **§7.5.5.1** 多轮条目中「回答或 `agent.intent` 延续首轮话题」为 **人工**口径；**不**等价于「次轮 SQL 一定正确」。  
- 若产品对 **L3/L4** 有承诺，应在本子规或 P1 任务单中增加 **可重复用例**（固定表、固定追问句、期望 SQL 形态或期望行数范围）。

## 6. 验收清单（草案，供任务单引用）

- [ ] **基线**：两轮同一 `session_id`，第二轮 `load` 日志中历史条数 ≥ 1（或等价断言）。  
- [ ] **意图**：次轮 `agent.intent` 在人工判读下仍指向 **结构化查询**（若用户期望问数）。  
- [ ] **grounding（若宣称）**：次轮执行 SQL（或脱敏摘要）中含首轮已披露表名 / 合理 join。  
- [ ] **结果**：对「有男性行」的 fixture，次轮不得在无理由时返回空集；若数据确为空，应答中可区分「0 行」与「无法解析指代」。
