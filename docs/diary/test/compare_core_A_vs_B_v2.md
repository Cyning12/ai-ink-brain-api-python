## 1. 一句话结论（v2）

- **token 消耗**：在两边都使用“每行 12 tokens、输出按 4 字符≈1 token”的近似口径下，**B（走图谱）约 68.5k tokens，A（不走图谱）约 75k tokens**，B 约 **节省 6.5k（≈8.7%）**。
- **时间消耗**：按两边自报估算，**A ~28min，B ~36min**；在这次跑法里，**走图谱并没有更快**（原因主要是 B 明确包含 t_graph 阅读成本）。
- **产出可审计性**：B 明确依赖 `_manifest.json` / `_contract_manifest.json` 与 CI 门禁路径，且大量结论带 SQL/代码行号；A 的实现层细节更丰满（含 tests/ 与 env 必填表），更偏“可直接改代码”的讲义风格。

## 2. 关键指标对比（按结果文件口径）

### 2.1 时间（结果文件自报）

- **A**：t_total **~28 min**（scan ~2 / read ~18 / synthesis ~8）
- **B**：t_total **~36 min**（graph ~8 / read ~18 / synthesis ~10）

**解读**：
- 这次两边的时间拆分结构清晰，且都在“几十分钟”量级，较上一轮可比性显著提升。
- B 的时间中包含了明确的 **t_graph ~8min**；如果你的目标是“图谱是否缩短接手时间”，建议下一轮把 **B 的 read 范围**进一步收敛（严格按图谱锚点只读关键函数），否则 B 可能“又读图谱又读大段代码”，时间优势不明显。

## 3. 覆盖率/阅读策略差异（决定“省 token 但不省时间”的关键）

### 3.1 A 的阅读策略特征

- **更偏全量实现**：明确阅读了 `tests/*.py`（~1443 行）并把它纳入 token 统计；同时输出了更完整的“env 必填/可选表”与更多实现细节（如 header 上限、sync 删除策略差异等）。
- **成本结构**：主要 token 来自 `api/*.py ~5500 行` 与 `tests ~1443 行`。

### 3.2 B 的阅读策略特征

- **图谱先行 + 抽样代码**：读了 `_tech_graph` 约 1200 行，同时对大文件（`api/index.py`, `api/unified_chat.py`）采用“抽样行数”统计；`tests/` 未读。
- **额外产出**：把 `_contract_manifest.json` 与 CI 门禁 `.github/workflows/tech-graph-contract.yml` 纳入“运行与观测/契约”视角，适合做跨端稳定性与门禁审计。

### 3.3 为什么 B token 更省但时间不更快

- **省 token 的来源**：B 没有阅读 `tests/`，且对大文件按抽样计入；同时图谱内容比“通读实现细节”更浓缩。
- **时间不更快的来源**：B 把“读图谱”作为刚性步骤（~8min），同时仍花了 ~18min 做代码/SQL核验，导致整体时间被“叠加”。

## 4. 质量与风险点（对后续开发影响最大的差异）

### 4.1 A 的优势 / 风险

- **优势**：
  - 更适合直接进入改代码（尤其是 ingest/sync 删除策略差异、env 必填表、fallback/降级策略等“坑位”）。
  - 引入 tests 作为“行为契约”的证据源，降低误解实现细节的概率。
- **风险**：
  - A 明确列出了 `docs/text2sql/v1/sql/supabase_init.sql` 在目录扫描中未出现，但主体里仍把它当“构建 store 的来源”描述得较确定；建议把该点降级为“未确认”或补一次文件存在性验证（否则结论可能漂移）。

### 4.2 B 的优势 / 风险

- **优势**：
  - “契约/门禁/manifest”视角更强：适合做长期维护（尤其端点、RPC、env、SSE 契约变更的 CI 护栏）。
  - 更强调“图谱名词回链到代码/SQL”，整体可审计性更好。
- **风险**：
  - 多处以“抽样行数”代替“读全文件”，导致某些不确定性判断可能偏保守或偏误（例如 B 自己的“不确定性 #10”与正文“Unified chat 调用 save_debug_log”存在潜在自相矛盾，需靠全文搜索一次性确认）。

## 5. 可行动结论（你可以直接用在后续流程里）

- **如果你的 KPI 是“降低 token 成本”**：这轮结果显示 **走图谱确实省 token（~8.7%）**，且仍能产出“可接手级别”的地图与契约视角。
- **如果你的 KPI 是“更快完成一次工程可接手梳理”**：这轮并未体现时间优势；要让 B 更快，需要进一步把 B 的“代码核验范围”限制为：只读图谱锚点指向的 handler/关键函数 + 相关 SQL（而不是再扩到大量抽样）。
- **如果你的 KPI 是“准备动刀改实现”**：A 这轮更像“能直接开改”的资料包（包含 tests 与更细的实现/配置清单），建议在 A 的基础上补上 manifest/contract 的门禁视角，形成兼顾“可改 + 可守”的合并版产物。
