## Prompt A（禁用图谱）— 全量理解后端并输出消耗明细

你是一个新的代码审阅/架构理解 Agent。你的任务是：**在完全不使用 `docs/_tech_graph/` 的前提下**，对 `ai-ink-brain-api-python` 后端项目进行一次“工程可接手级别”的完整理解，并把你的**时间与 token 消耗**、**覆盖率**、**产出**以可对比的格式输出到指定结果文件。

### 0. 强制约束（必须遵守）

- **禁止读取**：`docs/_tech_graph/**` 下任何文件（包括 `00_main*`、`01_struct.md`、`10_flow_*.md`、`_manifest.json` 等）。
- **禁止偷看**：任何其它地方对图谱的复制内容（如果有文档引用了 `docs/_tech_graph/`，跳过该段，不要展开）。
- **事实来源**：只允许来自真实代码、真实 SQL、真实配置文件。禁止编造端点、RPC、表结构、环境变量。
- **输出必须包含“消耗明细”**：你需要给出可复核的估算方法与逐项累计。

### 1. 目标理解深度（工程可接手）

你的“理解完成态”必须能做到：

- **模块地图**：指出关键模块/文件职责、入口文件、核心调用链路。
- **主链路**：至少覆盖 RAG / ingest / unified chat / text2sql / FTS / supabase RPC（如果项目存在这些链路；以代码为准）。
- **数据与存储**：整理核心数据结构（以代码与 SQL 为准），包含“字段级别的必填/可选”判断（如果能从代码推断）。
- **运行与观测**：说明日志、debug 开关、失败路径、重试策略（以代码为准）。
- **改动指引**：给出“新增一个端点 / 调整检索策略 / 调整 ingest”分别会动哪些文件、风险点在哪里。

### 2. 工作方式（建议顺序，但可自行调整）

- 先用目录扫描建立文件地图（重点看 `api/`、`tools/`、`supabase/`、`docs/meta/`、`docs/tasks/`、配置示例等）。
- 用搜索定位入口：FastAPI app 初始化、路由注册、依赖注入、中间件、鉴权等。
- 对每条关键链路：从 handler 入口一路追到关键函数（召回、rerank、构造 prompt、调用 LLM、写日志、写 DB、返回响应）。
- 对数据结构：优先从 Pydantic/TypedDict/dataclass/SQL DDL 推断，再回到调用点验证。

### 3. 消耗统计口径（必须输出）

你必须输出以下 4 类指标，并给出估算方式：

1) **时间**：
- t_scan：目录/索引扫描耗时
- t_read：阅读与追链路耗时
- t_synthesis：结构化总结与写结果耗时
- t_total：总耗时

2) **Token（输入 / 输出 / 总计）**（允许估算，但必须可复核）：
- input_tokens_code：阅读代码产生的输入 token
- input_tokens_docs：阅读 docs（不含 `_tech_graph`）产生的输入 token
- input_tokens_shell_or_search：搜索/命令输出带来的输入 token
- output_tokens_result：你最终结果文档的输出 token
- total_tokens：合计

估算方法要求：
- 对“阅读文件”的输入 token：用 `行数 × 每行 token 估算值`（给出你选的每行 token 值，如 10/15/20，并解释原因）。
- 对“搜索输出”的输入 token：按输出行数估算。
- 对“最终结果”的输出 token：按你生成内容长度估算（例如按字符/词数换算 token），并写明换算系数。

3) **覆盖率**：
- 列出你读过的关键文件清单（至少 20 个“有意义的文件”或覆盖所有关键链路的最少集合），并标注每个文件的“目的/贡献”（一行说明即可）。
- 明确你没读但可能重要的区域（例如某目录你只抽样读了哪些）。

4) **不确定性清单**（必须写）：
- 哪些地方你无法从代码/SQL直接确认（例如某 env 是否必填、某 RPC 是否存在），你如何处理这种不确定性（例如不下结论、给出验证步骤）。

### 4. 输出文件（必须落盘）

把你的最终结果写入：

- `docs/diary/test/result_A_no_tech_graph.md`

结果文件结构必须使用以下固定标题（顺序不能变，便于 diff）：

1. 摘要（你认为项目是什么、核心能力是什么，<= 200 字）
2. 入口与模块地图（用列表；每项包含文件路径）
3. 关键链路（按链路分小节：入口 -> 关键函数 -> 外部依赖 -> 失败路径）
4. 数据结构与存储（以事实为准；禁止编造）
5. 运行与观测（debug 开关、日志点、重试/超时）
6. 改动指引（新增端点/改检索/改 ingest 三类）
7. 不确定性与验证步骤（列清单）
8. 消耗明细（时间 + token 逐项累计 + 估算方法）
9. 覆盖率（读过的文件清单 + 未覆盖说明）

### 5. 质量门槛（自检后再写结果）

- 任何端点名、表名、RPC 名称、env 名称，必须能指向具体文件/代码位置；否则放入“不确定性与验证步骤”，不要写成事实。
- 不要用“我猜/可能/大概”替代定位。要么定位到代码，要么明确“不确定”并给出验证方式。
