## Prompt B（强制走图谱）— 基于 `_tech_graph` 快速全量理解并输出消耗明细

你是一个新的代码审阅/架构理解 Agent。你的任务是：**严格以 `docs/_tech_graph/` 为唯一架构索引入口**，对 `ai-ink-brain-api-python` 后端项目进行一次“工程可接手级别”的完整理解，并把你的**时间与 token 消耗**、**覆盖率**、**产出**以可对比的格式输出到指定结果文件。

### 0. 强制约束（必须遵守）

- **必须先读图谱**：至少完整阅读
  - `docs/_tech_graph/00_main.md`
  - `docs/_tech_graph/00_main.ai.md`
  - `docs/_tech_graph/99_spec.md`
  - `docs/_tech_graph/99_mermaid_protocol.md`
  - `docs/_tech_graph/01_struct.md`
  - 以及与你识别到的实际链路相关的 `10_flow_*.md` / `11_flow_*.md` / `12_flow_*.md` / `13_flow_*.md` / `14_runtime_observability*.md` / `15_e2e_boundary*.md`
- **事实来源（禁止编造）**：任何端点、RPC、表、env、handler 的结论必须能回链到真实代码或 SQL；图谱仅作为索引与摘要，不允许凭图谱“补全不存在的东西”。
- **输出必须包含“消耗明细”**：你需要给出可复核的估算方法与逐项累计。

### 1. 目标理解深度（工程可接手）

你的“理解完成态”必须能做到：

- **模块地图**：指出关键模块/文件职责、入口文件、核心调用链路。
- **主链路**：至少覆盖图谱中存在的主流程，并用代码核验（RAG / ingest / unified chat / text2sql / FTS / supabase RPC / observability 等）。
- **数据与存储**：用 `01_struct.md` 提供的结构作为“候选”，再回到代码/SQL核验字段、required/optional 与实际使用方式。
- **运行与观测**：以 `14_runtime_observability*` 为索引，回到代码确认日志点、debug 开关、重试/超时。
- **改动指引**：给出“新增一个端点 / 调整检索策略 / 调整 ingest”分别会动哪些文件、风险点在哪里。

### 2. 工作方式（强制流程）

你必须按如下流程执行（便于和 Prompt A 对比）：

1) **图谱索引阶段**
- 读完上述必读图谱文件后，输出一个“你认为的主流程目录”（链路列表 + 每条链路应去读哪些文件）。

2) **代码核验阶段**
- 每条链路至少选择 1 个“入口 handler”与 2~4 个“关键函数/模块”做深入阅读，确保链路可追溯到实现。
- 对图谱中出现的端点/RPC/env/表名：抽样或全量核验其在代码/SQL中确实存在。

3) **结果合成阶段**
- 生成结构化总结，并完成消耗明细与覆盖率清单。

### 3. 消耗统计口径（必须输出，且与 Prompt A 相同）

你必须输出以下 4 类指标，并给出估算方式：

1) **时间**：
- t_graph：阅读图谱耗时
- t_read：阅读与追链路耗时
- t_synthesis：结构化总结与写结果耗时
- t_total：总耗时

2) **Token（输入 / 输出 / 总计）**（允许估算，但必须可复核）：
- input_tokens_graph：阅读 `docs/_tech_graph/**` 产生的输入 token
- input_tokens_code：阅读代码产生的输入 token
- input_tokens_docs：阅读非图谱 docs 产生的输入 token
- input_tokens_shell_or_search：搜索/命令输出带来的输入 token
- output_tokens_result：你最终结果文档的输出 token
- total_tokens：合计

估算方法要求：
- 对“阅读文件”的输入 token：用 `行数 × 每行 token 估算值`（给出你选的每行 token 值，如 10/15/20，并解释原因）。
- 对“搜索输出”的输入 token：按输出行数估算。
- 对“最终结果”的输出 token：按你生成内容长度估算（例如按字符/词数换算 token），并写明换算系数。

3) **覆盖率**：
- 列出你读过的关键文件清单，并标注每个文件的“目的/贡献”（一行说明即可）。
- 明确你没读但可能重要的区域（例如某目录你只抽样读了哪些）。

4) **不确定性清单**（必须写）：
- 哪些地方你无法从代码/SQL直接确认（例如某 env 是否必填、某 RPC 是否存在），你如何处理这种不确定性（例如不下结论、给出验证步骤）。

### 4. 输出文件（必须落盘）

把你的最终结果写入：

- `docs/diary/test/result_B_with_tech_graph.md`

结果文件结构必须使用以下固定标题（顺序不能变，便于 diff）：

1. 摘要（你认为项目是什么、核心能力是什么，<= 200 字）
2. 图谱索引总结（你从图谱得到的“主流程目录”）
3. 入口与模块地图（用列表；每项包含文件路径）
4. 关键链路（按链路分小节：入口 -> 关键函数 -> 外部依赖 -> 失败路径）
5. 数据结构与存储（先引用 `01_struct.md` 再用代码/SQL核验）
6. 运行与观测（以图谱为索引回链到代码）
7. 改动指引（新增端点/改检索/改 ingest 三类）
8. 不确定性与验证步骤（列清单）
9. 消耗明细（时间 + token 逐项累计 + 估算方法）
10. 覆盖率（读过的文件清单 + 未覆盖说明）

### 5. 质量门槛（自检后再写结果）

- 图谱中的名词必须“回链”到代码或 SQL；回链不到的放进“不确定性与验证步骤”，不要写成事实。
- 不要用“我猜/可能/大概”替代定位。要么定位到代码，要么明确“不确定”并给出验证方式。
