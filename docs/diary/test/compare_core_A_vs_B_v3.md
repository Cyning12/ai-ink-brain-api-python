## 2. KPI 加权结论（先叙述后打分）

### 2.1 P1 易交接（权重 40%）

**胜者**：**B（略胜）**

**依据**：

| 维度 | A | B |
|------|---|---|
| **冷启动接手清单** | 12 步，偏「装依赖 → 跑 SQL → uvicorn → curl/pytest」，落地性强，步骤短。 | 13 步，显式纳入 **图谱目录、`_manifest.json`、SSE 契约、`tools/*` 校验与 CI 工作流**，与仓库真实约束对齐更好。 |
| **锚点索引表** | HTTP/RPC/表/env 与行号/m 区块结合较密，便于跳代码。 | 同上级别 + **manifest / `_contract_manifest.json`**，并写清 handler 别名（如 `unified_chat_route`）。 |
| **新人 FAQ** | 8 条，偏运行时行为（鉴权、`x-sources`、tool 预留）。 | 8 条，多了 **manifest 与路由对齐、CI 防漂移、双轨 `00_main`、图中 RPC 缩写与实现差异**，更利于「接手维护」而非仅本地跑通。 |
| **改动配方卡** | 三卡齐全；**新增端点未强调 `_manifest.json`/图谱更新**——在本仓属于高风险遗漏。 | **新增端点卡明确要求 manifest + `tech_graph_manifest_check.py`**；检索/ingest 亦指向契约与日志验证，更符合「下一任不踩 CI」的交接目标。 |

**简述**：

若交接对象是「要能长期改后端且不踩 CI / 契约门禁」的 Agent 或新人，**B 的接手清单与配方卡在制度层更完整**。A 在「最短路径跑起来 + 行号锚点」上仍很强，建议在后续版本中把 **manifest/契约** 并入 A 的配方卡（不必读图谱全文，但至少引用 `_manifest.json` 与有关脚本）。

---

### 2.2 P2 可靠性（权重 35%）

**胜者**：**B（胜）**

**量化辅助**：

| 指标 | A | B |
|------|---|---|
| 事实断言条数（表中条目） | 约 8 条 | 约 9 条（含 CI、契约、manifest） |
| 低置信 / 不确定条目 | 有「中」置信一条（部署）；§8 不确定性列表偏实现边角 | **显式标出图谱与实现的命名差异**（如 `13_flow` 中 RPC 缩写）、**PROJECT_CONFIG 与 `.github/workflows/` 现状可能不一致**，属于主动防漂移 |
| 明显无证据的硬性断言 | 未见明显硬伤 | 未见；且对「图中路径不存在」类问题有披露 |

**简述**：

B 在本轮把 **「图谱/CONFIG 可能过期」当作一等公民**写进断言与不确定性（含 `_manifest.json`、workflow、contract check），更贴合本仓库「真值 + 门禁」的形态。**A** 的断言表也很扎实，但对 **CI/manifest 契约线**覆盖较少，长期可靠性叙事弱于 B。

### 2.3 P3 省钱（权重 15%）

**胜者**：**A（胜）**

| 指标 | A | B |
|------|---|---|
| total_tokens（结果文档自报/粗算） | 读入合计约 **79 000**，输出约 **11 000**，总量约 **90 000** 量级（文档内拆分） | 以「图谱约 2000+ 行×10 + 代码」描述为主，**未给可与 A 逐项对齐的总表**；从文意看阅读图谱与 manifest **输入侧更重** |
| 备注 | 估算公式与分项较利于复盘 | 信息密度高；若计入图谱阅读，**同等实验协议下通常 token 不低于 A** |

### 2.4 P4 省时（权重 10%）

**胜者**：**A（胜）**

| 指标 | A | B |
|------|---|---|
| t_total（自报） | 约 **50 min** | 约 **90–120 min**（或写作 1.5–2 h 量级） |
| 备注 | 自报仍为估算，建议下轮用墙钟统一 | 读图谱 + 核验 CI/contract **天然更耗时**；与 KPI「省时」排序靠后一致——**可接受** |

## 3. 综合结论（服从 P1>P2>P3>P4）

在本轮 V3 结果下，按既定 KPI：**P1、P2 均由 B 占优**，**P3、P4 由 A 占优**。加权后整体结论为：**以「新人/新 Agent 可交接 + 少漂移」为主目标时，本轮更倾向采用 B 类产出范式**（图谱索引 + manifest/契约/CI + 代码核验）；同时保留 A 中的强项——**更细的代码行区间锚点、更明确的 token/时间分项**，便于下一轮把 B 的成本数字收紧到与 A 同级口径。

一句话：**要「合规交接与防漂移」，选 B 的结构；要「同样协议下成本与时间标尺」，补充 A 的计量方式。**

---

## 4. 下一轮改进建议（可选）

1. **统一计量**：要求 B 侧也填报与 A 同结构的「读入 tokens 分项表」（图谱行数×系数单列一行），否则 P3 只能定性。
2. **统一墙钟**：两端用外部计时记录「Prompt 开始到结果文件落盘」，降低自报偏差。
3. **合并配方卡**：A 的「新增端点」卡必须增加：**更新 `docs/_tech_graph/_manifest.json` + 本地跑 `python tools/tech_graph_manifest_check.py`**（无需读全图谱，但必须执行门禁动作）。
4. **抽检 PROJECT_CONFIG**：对 `PROJECT_CONFIG_AI_INK_BRAIN_API_PYTHON.md` 中与 `.github/workflows/` 矛盾的句子做一次 PR 修正，避免交接文档永久打架。
