## 2026-04-22: 后端总结 - Unified Chat（RAG+Text2SQL+Chain）与 SSE、路由器

### 今日结论（TL;DR）

- 完成 **Text2SQL v1** 最小闭环（检索 DDL+样例 → 生成 SQL → 只读校验 → 执行 → 总结），并补齐端到端验收文档。
- 引入 **Chain Timeline** 的统一事件模型 `events[]`，新增 `POST /api/py/chain/chat`（先覆盖 Text2SQL）。
- 新增 **Unified Chat**：`POST /api/py/unified/chat`（一次性 JSON events）与 `POST /api/py/unified/chat/stream`（SSE 流式 events）。
- 新增 **Intent Router v1**：在 Unified 中自动选择 `rag/text2sql/no_data`，并输出可观测事件 `router.decision`（why + evidence）。
- 关键踩坑：本地多项目 `.env` 污染、Supabase Pooler 用户名格式、RLS policy 导致“可见行数为 0”、FAISS 依赖缺失导致 500。

### 关键决策（Why + What）

- **为什么新增 Unified 而不改旧 `/chat`**：
  - 旧 `/api/py/chat` 为流式纯文本，改动风险高；Unified 作为新入口可并行验证与渐进替换。
- **为什么引入 `events[]`**：
  - 仅有“最终回答”无法调试工具链；`events[]` 让前端能完整展示 chain（工具调用、SQL 结果、sources、latency、error）。
- **为什么 v1 用 SSE 方案 A**：
  - 浏览器与 Next BFF 易透传，前端可增量 append timeline；v1 优先实现“事件实时”，token 级流后续再做。
- **为什么 Intent Router 不先做“意图配置表”**：
  - v1 路由规则迭代快，建表会带来权限/审计/回滚复杂度；先用代码内可配置规则+证据校验，便于版本化与回溯。

### 实现要点（How）

#### 1) Text2SQL v1

- 语料：从初始化 SQL 与样例文档抽取 DDL / 示例问答。
- 检索：FAISS 优先；缺失时降级为 fallback store（纯 Python 相似度排序）。
- 安全：SQL 只读校验（仅 SELECT/WITH…SELECT），执行阶段限制返回行数。
- 结果总结：对 count/cnt 等聚合结果做确定性总结，避免 LLM 把 `count=0` 误判为“未查到数据”。

#### 2) Chain Events（timeline）

- 事件类型（v1）：`tool.call.start/end`、`sql.result`、`rag.sources`、`assistant.message`、`error`、`latency`。
- 结构：每条事件包含 `type/ts/step_id/payload`，前端可排序渲染。

#### 3) Unified Chat（一次性 JSON + SSE）

- JSON：`/api/py/unified/chat` 返回 `{ ok, run_id, mode, events[] }`。
- SSE：`/api/py/unified/chat/stream` 按阶段输出 `event: chain`（data 为单条 event JSON），结束输出 `event: done`。
- RAG v1：优先保证事件完整，可先非流式生成最终 answer，再发 `assistant.message`。

#### 4) Intent Router v1（raw query）

- 路由决策遵循：
  - **意图识别用 raw query**
  - RAG 检索可扩展为 raw+rewrite 双路（后续迭代）
  - Text2SQL 全程使用 raw query
- 可观测：输出 `router.decision`，包含 `candidate_mode/final_mode/rule_hits/evidence/fallback`。

### 指标与观测（latency / logs / thresholds）

- `events[]` 中统一提供 `latency`（total + stages_ms），使 UI 层可直接展示耗时分解。
- `router.decision` 中记录 evidence（ddl_hits / fts_hits 等），用于解释路由原因与定位误路由。

### 坑位与排障（Symptoms / Root Cause / Fix）

1) **FAISS 缺失导致 500**
- 症状：Text2SQL store 初始化时报 “Missing dependency: faiss-cpu”。
- 根因：运行环境未安装 `faiss-cpu`。
- 修复：降级 fallback store + 输出可开关日志（`TEXT2SQL_DEBUG=1`）。

2) **Supabase 直连/Pooler/用户名格式导致连接失败或可见行数为 0**
- 症状：连接失败（tenant/user not found）或 `count(*)=0` 但控制台可见数据。
- 根因：Pooler 用户名需携带 project ref；或 RLS policy 未对只读角色放行。
- 修复：使用 Transaction Pooler 的连接串；对 Text2SQL 相关表增加 `FOR SELECT TO text2sql_readonly USING (true)` 的 policy。

3) **本地多项目 `.env` 污染导致 SiliconFlow key 401**
- 症状：LLM 请求返回 401 key invalid，但控制台 key 正常。
- 根因：错误加载了另一个项目的环境变量。
- 修复：启动与自检时显式指定 dotenv 路径或 `source .env`，避免跨目录污染。

4) **路由器误伤：SQL 意图被回退到 no_data**
- 症状：明显 SQL query 被 `fallback` 到 `no_data`。
- 根因：证据校验阈值/得分标定不可靠导致 ddl_hits=0。
- 修复方向：降低阈值、加入“表名字符串候选召回 + LLM 判别器”替代纯分数阈值（后续任务）。

### 原理学习总结（今日沉淀）

- **为什么需要事件模型而不是“只返回答案”**：
  - 可观测性是 Agent/RAG 系统的第一性需求；无事件就无法定位“改写/embedding/检索/执行/总结”的哪一步出错。
- **SSE 适合 v1 的原因**：
  - 消费端简单，服务端实现为生成器即可；比起 WebSocket/复杂协议更易在 BFF 透传。
- **意图路由的核心不是“分类模型”，而是“证据链”**：
  - 规则只负责候选；最终决策应基于 evidence（schema/FTS 命中等），并把 why 输出到日志/事件。
- **RLS 是“看不见数据”的常见根因**：
  - 直连用户 ≠ authenticated/anon 角色；policy 不匹配就会出现“查询成功但返回 0 行”的错觉。
