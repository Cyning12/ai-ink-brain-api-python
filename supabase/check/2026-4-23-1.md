# 2026-4-23 阶段总结（1）

> 本文是阶段小结（后续还会有阶段总结，最终再汇总）。

## 本阶段目标

针对回归中 **RAG 检索 0 hits** 与网络偶发 `Connection reset by peer` 的问题，优先把 RAG 检索链路做成：

- **可用**：网络抖动不至于直接 0 hits
- **可解释**：即便 0 hits 也能看出是 keyword/vector 哪路没命中、是否 embedding 失败、是否发生重试
- **更稳**：对日期类 query（`2026-4-14` vs `2026-04-14`）提升 keyword 命中率

## 关键发现（数据库侧）

- `public.documents` 数据是存在的（总量、embedding、fts_tokens 都齐全）。
- 第 3 步（FTS/keyword）对日期字符串非常敏感：`2026-04-14` 能命中，但 `2026-4-14` 可能 0 行（`'04' != '4'`）。
- `plainto_tsquery` 的 **AND 语义**会把“日记”变成必须命中的约束词：`2026-04-14 日记` 若正文不含“日记”会直接 0 行。
- 仓库内 `supabase/sql/hybrid_search.sql` 的 `keyword_documents` 已使用 `websearch_to_tsquery`（更贴近“搜索框语义”）。

## 已完成改动（后端链路）

### 1) Unified RAG：raw + rewrite 双路 keyword 召回 + 融合

- 同时调用：
  - `keyword_documents(raw_query)`
  - `keyword_documents(rewritten_query)`
- 两路 keyword 先 RRF 融合，再与 vector hits 融合，降低单路漏召回。

### 2) Supabase RPC：有限重试兜底

对 `match_documents` / `keyword_documents` 增加有限重试（可配置次数），覆盖 `connection reset/timeout/broken pipe` 等可恢复错误，降低网络抖动造成的“硬 0 hits”。

### 3) 可解释事件增强（JSON + SSE 一致）

在 `rag.retrieve` 的 `tool.call.end.payload.output` 增加：

- `keyword_hits_raw`
- `keyword_hits_rewrite`
- `retry_count`
- `embedding_error`

用于明确区分“库里无数据” vs “链路失败/策略漏召回”。

### 4) 查询侧日期归一化（Keyword Only）

针对 `YYYY-M-D` / `YYYY-MM-DD` 等日期形态，生成多候选并拼成 websearch OR 语句（带双引号）：

- `"2026-04-14" OR "2026-4-14" OR "2026/04/14" OR ...`

只影响 keyword 查询参数，不改变原始 query 的展示与生成。
